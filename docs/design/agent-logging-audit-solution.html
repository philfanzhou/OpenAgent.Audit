核心结论

  1. 保护目标：不让审计与观测链路成为新的泄露出口：因排障、审计而能访问观测系统的人，不会因此看到原本看不到的个人信息（见第 07 节）。会话业务存储与审计存储分离——恢复 / 继续会话走业务自有在线存储（如 Postgres），本方案只承载审计与观测数据。
  2. prompt 与每次模型返回交给 Langfuse 开源版：一次请求是一棵 trace 树；trace 中的敏感值只以「编号 + 掩码」出现，不含原文，也不含密文。
  3. 审计脱敏采用「展示时脱敏」（模式 B，已选定）：入库时同时生成掩码与密文——掩码随 trace 供日常浏览，全程不解密；密文（AES-256-GCM，公钥包裹数据密钥）单独存入审计域密文表，只有 decrypt-svc 能经 KMS 解密，单条审批、全程留痕。
  4. 媒体放 S3 兼容对象存储（SeaweedFS / MinIO）：Agent 端用同一把公钥加密后直传，trace 只存 s3:// key + 哈希 + MIME 引用；查看原件与还原原文走同一审批流程。
  5. 审计日志存独立防篡改表，Loki 只做服务日志与告警：Loki 只索引标签、单行有大小上限、没有 trace 结构，不承担 prompt 存储；审计日志正本写入 append-only 表并归档到 Object Lock 桶，Loki 只收副本用于实时告警。

存储边界：会话业务存储与审计存储是两套独立存储——业务侧的会话状态与历史会话恢复由业务自有在线库（如 Postgres）承载；本方案的 Langfuse / 审计域 / S3 / Loki 只承载审计与观测数据（append-only），不作为业务数据源，双方以 conversation id 关联。

02

数据传递：Agent 如何把数据交给 Langfuse / 审计域 / S3 / Loki

三条通路各自独立、并行工作，同一次请求的数据最终以 trace_id 汇合；脱敏与上报都在后台导出线程执行，不占用请求线程。

1 trace 与密文

Agent → Langfuse / 审计域

Langfuse Python SDK · 批量 flush · HTTPS
SDK 装饰器捕获 进程内缓冲 导出线程脱敏 密文写入密文表 掩码 span 批量发送 ClickHouse / Postgres
  • 不占用请求线程：脱敏钩子 mask_otel_spans 在后台导出线程执行；Python GIL 争用仍会间接影响请求延迟，上线前必须压测
  • 出进程前脱敏：离开 Agent 进程的 span 只含「编号 + 掩码」；密文不进 Langfuse，单独写入审计域密文表
  • 失败即丢弃（fail-closed）：钩子抛异常时整批丢弃、绝不明文导出；队列满时同样丢弃——必须监控丢弃数，大于 0 即告警
  • 密文写入可靠性：写表失败时本地重试；仍失败则该编号无法还原，但掩码照常可看，不泄露信息
  • 单一路径：所有 Agent 统一用 Langfuse Python SDK 接入；不走纯 OTLP 导出（没有脱敏钩子），也不并行导出到其他后端（其他导出器拿到的是未脱敏数据）
2 媒体原件

Agent → S3

公钥加密 · S3 SDK 直传 · SSE-KMS
收到图片 / 文件 sha256 + 校验 公钥信封加密 S3 PUT（SSE-KMS） 引用替换 base64 引用随 trace 入库
  • 应用直传：文件字节不经过 Langfuse 管道，也不开启 Langfuse 媒体上传；进入 trace 的只有引用（s3:// key + sha256 + mime）
  • 客户端加密：用与文本相同的公钥加密后再上传，桶管理员读到的也只是密文；SSE-KMS 只是静态加密的第二层，挡不住有读权限的人
  • 先替换再上报：base64 替换成引用之后，才交给 ① 的上报通路——trace 体积可控，SDK 也不会自动上传媒体
  • 查看原件：与还原原文同一流程（申请 → 审批 → decrypt-svc 解密 → 留痕）
3 服务日志

Agent → Loki

stdout 采集 · push API
stdout 输出 JSON 日志 Promtail / Alloy 采集 Loki push API Loki 存储
  • 只放轻数据：错误、元数据——每条带 trace_id / session_id 字段，便于与 trace 互跳
  • 审计事件副本：audit-web / decrypt-svc 的审计事件另推一份到 Loki，只用于实时告警（如短时间内大量解密）；正本在审计日志表
  • 基数警告：user_id、trace_id 这类高基数字段放 JSON 字段、不要做 label，否则索引爆炸；查询时用 JSON 解析过滤
  • 小规模直推：可用 Loki HTTP API 或容器 logging driver 直推，省掉采集器

汇合方式：Langfuse trace 是锚点——日志按 trace_id 在 Loki 检索（{"trace_id"="…"}），媒体按 s3:// key 从对象存储取回，密文按实体编号在密文表中定位，各通路的数据围绕同一次请求对齐。

记录成什么样：一次请求的 trace 树

示例结构：一条 trace 挂多个 span / generation，工具入参、token 与耗时全部入库；敏感值以「编号 + 掩码」形式出现（见第 08 节）。

04

标识符映射：conversation / user / agent id

conversation id 与 user id 是 Langfuse 一等字段，agent id 用 tag 承载——现有方案直接覆盖，无需扩展存储。

你的标识符Langfuse 落点说明
conversation idsessionId（一等字段）相同 sessionId 的所有 trace 及内部 observation 聚合成会话视图，支持整段回放；超过 200 字符会被丢弃
user iduserId（一等字段）跨 trace 关联用户；直接使用业务系统内部用户 ID（UUID / 自增 ID），不使用手机号、邮箱，也不对它们做哈希——无密钥哈希可被穷举还原
agent idtags（推荐）或 metadatatag 可在 UI 与 API 过滤（如 agent:cs-bot）；metadata 放非过滤用途的扩展信息
请求级 idtrace id / name每次用户请求一条 trace，自定义 trace id 与你的请求 id 对齐

多 agent 协作的两种建法

  • 一棵树：一条 trace 内把每个 agent 的执行建成嵌套 span，agent id 放 span 级 metadata——会话链路全貌在一处
  • 一人一线：每个 agent 一轮一条 trace，共享 sessionId + 各自 agent tag——按 agent 维度统计更方便

两者可混用：主干一棵树，关键 agent 另行打点。

上报与查询细节

  • 上报：在根 observation 内用 propagate_attributes(session_id, user_id, tags) 设置，子 observation 自动继承
  • 查询：按 session / user / tag / 时间范围过滤；API GET /api/v2/traces?sessionId=…。不支持按手机号、身份证号反查会话（见第 08 节）
  • 多租户：org id 非一等字段，用 tag 或按租户分 project
05

为什么 Loki 不适合存 prompt

单行大小上限

ingestion 按 max_line_size 限制单行，长上下文 prompt 很容易超限，被截断或拒收。

只索引标签

只索引 label 与时间戳，内容检索等于全量扫描；大 JSON 行会让查询从毫秒级恶化到超时。

没有 trace 结构

一次 agent 请求是多轮嵌套 span（模型、工具、重试），扁平日志流表达不了这种父子关系。

展示与查询截断

前端约 8,191 字符处截断；对大行做 JSON 字段提取的成本随数据量陡增。

→ Loki 的位置：继续收普通服务日志和审计事件副本（告警用），prompt 存储让位给 tracing 平台，审计日志正本另存防篡改表。

07

威胁模型：保护范围

保护目标：不让审计与观测链路成为新的泄露出口——因排障、审计等原因能访问观测系统的人，不会因此看到原本看不到的个人信息。业务库有自己的权限控制，访问者少、以程序访问为主；观测系统则是开发者、审计员、运维每天都在看，数据还常被导出、截图、贴进工单。

在范围内

本方案防护
  • 开发者通过 Langfuse UI / API 查看 trace：只看到编号 + 掩码
  • 审计员日常浏览：只看到掩码；还原原文须审批并留痕
  • 可观测平台运维直接读取 ClickHouse / S3 / 备份：只有掩码与密文
  • Langfuse / ClickHouse / S3 数据整体泄露：没有私钥就无法还原
  • Agent 配置或密钥泄露：Agent 只持公钥，解不开历史数据

不在范围内

由其他措施负责
  • 业务库访问者：业务会话库存完整明文，由业务系统的权限控制负责
  • LLM 供应商：收到完整明文 prompt，由供应商协议与数据出境评估负责
  • 运行中的 Agent 进程：处理中的明文在内存里，进程被攻破时实时数据可见（历史数据仍不可解）
  • 未被识别的敏感信息：识别存在漏报，按召回率指标管理剩余风险（见第 11 节）

待合规确认：开发者在 Langfuse UI 中可以看到未被识别的对话明文，且 Langfuse 开源版不记录浏览留痕，这一点是否可以接受。

08

审计与展示时脱敏（模式 B · 已选定）

模式 A · 入库前脱敏

备选

masking 函数在发送前把敏感值替换为掩码，Langfuse 只存掩码数据（Langfuse 官方 masking 即此模式）。实现最简单，但不可逆——审计员无法核验原文。

模式 B · 掩码浏览 + 密文核验

已选定

入库时对每个敏感实体同时生成掩码与密文：掩码随 trace 入 Langfuse，日常浏览无需解密；密文用 AES-256-GCM 加密、数据密钥用公钥包裹（非对称信封加密），单独存入审计域密文表。Agent 只持公钥、只能加密；私钥只在 KMS，只有 decrypt-svc 能调用。代价是要自研加密 operator、密文表与审批流程。

① 入库

Agent 导出线程中 Presidio 识别敏感实体，生成掩码 + 公钥加密的密文；span 中只留「编号 + 掩码」，密文写入密文表。媒体同样公钥加密后上传。

② 展示

audit-web 直接渲染 trace 中的掩码，全程不解密；审计员浏览了哪段会话同样写入审计日志。

③ 核验

合规主管申请还原单条记录 → 审批 → decrypt-svc 读取密文表并经 KMS 解密；申请、审批、解密都写入审计日志。

同一条消息在审计链路中的三种视图

帮我联系下 张 *，电话 138****5678，身份证 110101********8515，邮箱 z*****i@example.com，卡号 6222 **** **** 0000。

审计界面默认渲染：直接读取入库的掩码，全程不解密。

帮我联系下 张伟，电话 13812345678，身份证 110101199003078515，邮箱 zhangwei@example.com，卡号 6222 0202 0000 0000。

授权核验视图：仅合规主管经审批后可见，限单条、全程留痕。

Langfuse trace 中存储的内容（只有编号 + 掩码）：

帮我联系下 ⟦NAME#9f2c81e3a07b6d12|张 *⟧，电话 ⟦PHONE#71b03ea7c4e12b90|138****5678⟧，身份证 ⟦IDCARD#3ad80712f95e0c47|110101********8515⟧，……

审计域密文表（只有 decrypt-svc 能读取）：

编号类型密文
9f2c81e3a07b6d12NAMEAQ3vZk9TxW…（约 100 字符）…r2Kd0w
71b03ea7c4e12b90PHONEAQb81LmQe4…（约 110 字符）…Xv7HcA

每条密文约 100+ 字符（随机数 + 密文 + 认证标签 + 公钥包裹的数据密钥），同一实体每次加密结果都不同。编号随机生成，不由原文派生。删除密文表中的行，对应实体即永久无法还原。

演示为静态示意；真实密文由自研 encrypt operator 生成。掩码规则（张 *、138****5678 等）按实体类型配置。

角色使用入口与默认视图能否还原原文典型用途
审计员audit-web · 掩码视图不可日常合规抽查、对话抽样审查
合规主管audit-web · 掩码视图，可申请还原可 · 审批后由 decrypt-svc 解密并留痕争议处理、安全调查核验
开发者Langfuse UI · 编号 + 掩码 + 技术元数据不可排障：token 用量、延迟、错误

防旁路：Langfuse、API 与导出中本来就只有编号与掩码，密文只在密文表中、且只有 decrypt-svc 能读取——旁路在数据结构上被切断，不依赖渲染层遮挡。

审计日志：浏览会话、申请 / 审批还原、实际解密、角色变更，全部写入审计域的 append-only 审计日志表——应用账号只有 INSERT 权限，每条记录包含上一条的哈希（哈希链），删改即可被发现；定期归档到开启 Object Lock（一次写入、不可删除）的 S3 桶。保留期不少于六个月（《网络安全法》第 21 条）。

检索范围：审计查询只支持按 userId、sessionId 与时间范围；不支持按手机号、身份证号反查会话（密文随机化、编号随机生成）。因此用户的删除请求只覆盖其本人会话，他人对话中提及的信息不在删除范围内。

中文识别要点：Presidio 需通过 NlpEngineProvider 配中文 spaCy 模型（如 zh_core_web_sm）；身份证、手机号、银行卡用自定义 recognizer（正则 + 校验位，如 (?<!\d)1[3-9]\d{9}(?!\d)、18 位身份证校验、Luhn），正则要加数字边界，并覆盖空格 / 横线分隔、全角数字等变体；中文人名召回一般，建议规则 + 模型混合，必要时用 OpenPipe pii-redact（LLM 检测）兜底。

待合规确认：① 各类实体的掩码规则（保留几位）——如 138****5678 露出 11 位中的 7 位，结合其他信息存在重识别风险，可考虑只保留后 4 位；② 审计日志的具体保留期限（六个月或更久）；③ 删除请求只覆盖用户本人会话是否可以接受。

09

多模态：图片与文件

请求里本来就是 URL

直接记录 URL 引用，不搬运文件。注意源可能失效，重要场景可异步镜像到自家 bucket（同样先加密）。

base64 / 用户上传

先在 Agent 端用公钥加密并上传对象存储，再把消息里的 base64 替换成引用后才入 trace；否则单条 trace 轻松数 MB，原件也会绕过脱敏。

查看原件

审计员默认只看到占位符，如 [图片 · image/png · 183KB]；查看原件走还原审批流程，由 decrypt-svc 解密并留痕。

message.json
// 记录前：原始 message（数 MB）
{"type": "image_url", "image_url": {"url": "data:image/png;base64,iVBORw0…"}}

// 记录后：trace 里实际入库的内容（原件已公钥加密并上传）
{"type": "image_url", "image_url": {"url": "s3://agent-media/2026/…/x.png.enc"},
 "meta": {"sha256": "9f2c…", "bytes": 183421, "mime": "image/png", "enc": "envelope/aes-256-gcm"}}

为什么必须加密：Presidio 只处理文字，身份证照片、银行卡照片、聊天截图里的信息不会被识别；人脸照片还属于《个人信息保护法》第 28 条规定的敏感个人信息。SSE-KMS 只防介质丢失，有桶读权限就能读到原件。

存储选型注记：SeaweedFS 小文件性能与存储效率更好、许可宽松；MinIO 文档与生态最全。两者皆可，看运维熟悉度；审计日志归档桶需要 Object Lock，选型时确认支持情况（MinIO 支持）。

# 骨架示意：Langfuse Python SDK v5，API 以 SDK 文档为准
from langfuse import observe, propagate_attributes

@observe()                                            # 根 observation = 一次用户请求
def handle_request(req):
    with propagate_attributes(
        session_id=req.conversation_id,               # conversation id
        user_id=req.internal_user_id,                 # 业务内部 ID，不用手机号 / 邮箱
        tags=[f"agent:{req.agent_id}"],               # agent id 走 tag
    ):
        return call_llm(req.messages)                 # 内部再包 @observe → generation span

自研框架提示：若不使用官方集成框架，手动埋三个关键点即可起步——请求入口、LLM 调用、工具调用；工具入参与返回摘要挂在 span 上。

3Presidio 中文脱敏管线（写入侧，必须开发）

pii_pipeline.py
# 骨架示意：识别 → 掩码 + 加密 → 密文写表；挂在导出线程（mask_otel_spans）
import secrets
from presidio_analyzer import AnalyzerEngine, Pattern, PatternRecognizer
from presidio_analyzer.nlp_engine import NlpEngineProvider
from langfuse import Langfuse
from langfuse.types import MaskOtelSpansResult, OtelSpanPatch

nlp = NlpEngineProvider(nlp_configuration={
    "nlp_engine_name": "spacy",
    "models": [{"lang_code": "zh", "model_name": "zh_core_web_sm"}],
}).create_engine()
analyzer = AnalyzerEngine(nlp_engine=nlp, supported_languages=["zh"])
analyzer.registry.add_recognizer(PatternRecognizer(
    supported_entity="CN_PHONE", supported_language="zh",
    patterns=[Pattern("cn-mobile", r"(?<!\d)1[3-9]\d{9}(?!\d)", 0.95)]))
# 同理注册：18 位身份证（校验位）、银行卡（Luhn）

# seal(raw)：AES-256-GCM 加密原文，数据密钥用公钥包裹（Agent 只持公钥）
# mask(type, raw)：按实体类型生成掩码，规则待合规确认
# vault：审计域密文表，Agent 账号只有 INSERT 权限；实际实现应批量写入并重试
def protect(text: str) -> str:
    out, last = [], 0
    for r in sorted(analyzer.analyze(text=text, language="zh"), key=lambda r: r.start):
        if r.start < last:                            # 跳过重叠实体
            continue
        raw = text[r.start:r.end]
        eid = secrets.token_hex(8)                    # 随机编号，不由原文派生
        vault.insert(eid, r.entity_type, seal(raw))
        out += [text[last:r.start], f"⟦{r.entity_type}#{eid}|{mask(r.entity_type, raw)}⟧"]
        last = r.end
    return "".join(out + [text[last:]])

TEXT_KEYS = ("langfuse.observation.input", "langfuse.observation.output")  # 键名以 SDK 文档为准

def mask_otel_spans(*, params):                       # 导出线程执行；抛异常 → 整批丢弃（fail-closed）
    patches = {}
    for sid, span in params.spans.items():
        changed = {k: protect(v) for k, v in span.attributes.items()
                   if k.startswith(TEXT_KEYS) and isinstance(v, str)}
        if changed:
            patches[sid] = OtelSpanPatch(set_attributes=changed)
    return MaskOtelSpansResult(span_patches=patches)

langfuse = Langfuse(mask_otel_spans=mask_otel_spans)

召回率调优是持续工作：中文人名 NER 一般，规则 + 模型混合，必要时用 OpenPipe pii-redact（LLM 检测）兜底；效果用标注测试集衡量（见上文验收口径）。

4审计展示层（读取侧，最大自研部分，无现成开源整体方案）

audit-web · 审计前端

三级角色视图；直接渲染 trace 中的掩码；还原申请与审批入口。浏览、申请、审批全部写审计日志。可做得很薄：会话列表 + trace 详情页 + 审批页。

audit-api · 查询

查 Langfuse API 拉取 trace（只含编号 + 掩码）；按 userId / sessionId / 时间检索；导出内容同样只有掩码。

decrypt-svc · 解密服务

唯一能读取密文表、唯一能经 KMS 使用私钥的组件；只受理已审批的单条还原（文本实体与媒体原件）；每次解密写入审计日志，独立部署、单独审计。

配套：审计日志表（应用账号只有 INSERT + 哈希链，定期归档到 Object Lock 桶）；保留期定时任务（按期调用 Langfuse API 删除过期 trace，同步删除密文表对应行，S3 生命周期清理事件桶与媒体桶）。读取侧完成前，开发者可临时用 Langfuse UI 浏览（只有编号 + 掩码），但没有角色区分和浏览留痕，不能替代审计。

性能提示：Presidio 在导出线程中运行，不占用请求线程，但 Python GIL 争用会间接增加请求延迟，上线前必须压测。多轮会话中每次 LLM 调用都带完整历史，同一段文本会被反复识别——可在进程内按文本哈希缓存脱敏结果。导出队列满时数据会被丢弃，丢弃数必须监控。

容量提示：多轮会话的 trace 体积膨胀快，ClickHouse 保留期建议先紧后松，S3 配生命周期归档，媒体桶与事件桶分开计费观察；密文表随实体数增长，按保留期同步清理。
