核心结论

  • Loki 不承担 prompt 存储：只索引标签、单行有大小上限、没有 trace 结构。它继续做普通服务日志（错误、审计事件、元数据）。
  • prompt 与每次模型返回交给 LLM tracing 平台：一次请求是一棵 trace 树，自托管首选 Langfuse（核心 MIT，v3 生产可用）。
  • 媒体放 S3 兼容对象存储（SeaweedFS / MinIO），trace 只存 s3:// key + 哈希 + MIME 引用。
  • 审计脱敏采用「展示时脱敏」（模式 B，已选定）：Presidio encrypt 以 AES-256 把敏感值变成可逆密文 token 入库，审计界面默认渲染掩码，合规主管经 KMS 授权才能还原并留痕。
  • 会话业务存储与审计存储分离：恢复 / 继续会话走业务自有在线存储（如 Postgres）；本方案的 Langfuse / S3 / Loki 仅承载审计与观测数据，不作为业务数据源。

02

数据传递：Agent 如何把数据交给 Langfuse / S3 / Loki

三条通路各自独立、并行工作，同一次请求的数据最终以 trace_id 汇合；观测数据全部在后台异步传递，不阻塞用户请求。

① trace 数据

Agent → Langfuse

SDK 批量 flush · HTTPS（/api/public/ingestion 或 OTLP）
SDK 装饰器捕获 进程内缓冲 后台批量 flush worker 异步处理 ClickHouse / Postgres
  • 非阻塞：上报在后台线程批量执行，不给用户请求加延迟；进程退出前 flush
  • 出进程前脱敏：masking 回调在 SDK 发送之前运行，离开 Agent 进程的已是密文 token / 掩码
  • 批量与重试：事件合并批量发送，失败重试与丢弃策略可配
  • 替代路径：已有 OTel 体系时走 OTel SDK → OTLP exporter → Langfuse OTLP 端点，语义一致
② 媒体原件

Agent → S3

S3 SDK 直传 · SSE-KMS
收到图片 / 文件 sha256 + 校验 S3 PUT（SSE-KMS） key 回填消息 引用随 trace 入库
  • 应用直传：文件字节不经过 Langfuse 管道，进入 trace 的只有引用（s3:// key + sha256 + mime）
  • 先替换再上报：base64 消息替换成引用之后，才交给 ① 的上报通路——trace 体积可控
  • 变体：开启 LANGFUSE_S3_MEDIA_UPLOAD_ENABLED 后，data URI 媒体可由 worker 上传到 Langfuse 配置的 bucket；自管 bucket 时自己上传、只给引用
③ 服务日志

Agent → Loki

stdout 采集 · push API
stdout 输出 JSON 日志 Promtail / Alloy 采集 Loki push API Loki 存储
  • 只放轻数据：错误、审计事件、元数据——每条带 trace_id / session_id 字段，便于与 trace 互跳
  • 基数警告：user_id、trace_id 这类高基数字段放 JSON 字段、不要做 label，否则索引爆炸；查询时用 JSON 解析过滤
  • 小规模直推：可用 Loki HTTP API 或容器 logging driver 直推，省掉采集器

汇合方式：Langfuse trace 是锚点——日志按 trace_id 在 Loki 检索（{"trace_id"="…"}），媒体按 s3:// key 从对象存储取回，三条通路的数据围绕同一次请求对齐。

03

记录成什么样：一次请求的 trace 树

示例结构：一条 trace 挂多个 span / generation，工具入参、token 与耗时全部入库；敏感值以密文 token 形式出现（见第 07 节）。

trace POST /agent/run user u_8d21（假名）· session 7f3a9c · tag agent:cs-bot · 总 4.2s · $0.0121
span接收请求用户输入（密文 token）+ 图片引用 s3://agent-media/…png（sha256: 9f2c…）
generationLLM 调用 #1glm-4.7 · in 1,248 tok / out 356 tok · 1.1s · prompt 与 completion 全文（密文 token）
span工具调用 web_search入参、返回摘要与耗时
generationLLM 调用 #2含工具结果 · in 2,010 tok / out 512 tok · 2.3s
span返回响应最终回复全文 + 引用媒体链接
04

标识符映射：conversation / user / agent id

conversation id 与 user id 是 Langfuse 一等字段，agent id 用 tag 承载——现有方案直接覆盖，无需扩展存储。

你的标识符Langfuse 落点说明
conversation idsessionId（一等字段）相同 sessionId 的所有 trace 及内部 observation 聚合成会话视图，支持整段回放；超过 200 字符会被丢弃
user iduserId（一等字段）跨 trace 关联用户，配 User 对象与分群做单用户分析；派生自手机号 / 邮箱时先假名化（见第 07 节）
agent idtags（推荐）或 metadatatag 可在 UI 与 API 过滤（如 agent:cs-bot）；metadata 放非过滤用途的扩展信息
请求级 idtrace id / name每次用户请求一条 trace，自定义 trace id 与你的请求 id 对齐

多 agent 协作的两种建法

  • 一棵树：一条 trace 内把每个 agent 的执行建成嵌套 span，agent id 放 span 级 metadata——会话链路全貌在一处
  • 一人一线：每个 agent 一轮一条 trace，共享 sessionId + 各自 agent tag——按 agent 维度统计更方便

两者可混用：主干一棵树，关键 agent 另行打点。

上报与查询细节

  • OTel 接入：langfuse.session.id / langfuse.user.id / langfuse.tags 须打在根 span 上，放 resource attributes 不生效
  • 查询：UI 按 session / user / tag 过滤；API GET /api/v2/traces?sessionId=…；自托管可直查 ClickHouse
  • 多租户：org id 非一等字段，用 tag 或按租户分 project
05

为什么 Loki 不适合存 prompt

单行大小上限

ingestion 按 max_line_size 限制单行，长上下文 prompt 很容易超限，被截断或拒收。

只索引标签

只索引 label 与时间戳，内容检索等于全量扫描；大 JSON 行会让查询从毫秒级恶化到超时。

没有 trace 结构

一次 agent 请求是多轮嵌套 span（模型、工具、重试），扁平日志流表达不了这种父子关系。

展示与查询截断

前端约 8,191 字符处截断；对大行做 JSON 字段提取的成本随数据量陡增。

→ Loki 的位置：继续收普通服务日志，prompt 存储让位给 tracing 平台。

07

审计与展示时脱敏（模式 B · 已选定）

模式 A · 入库前脱敏

备选

masking 函数在发送前把敏感值替换为掩码，Langfuse 只存掩码数据（Langfuse 官方 masking 即此模式）。敏感原文不出应用边界；但不可逆——审计员无法核验原文，需要另行自建加密映射表（vault）。

模式 B · 存储加密 + 展示脱敏

已选定

Presidio encrypt（AES-256-GCM）生成可逆密文 token 入库；审计界面按角色渲染掩码，持密钥授权后可还原。审计友好、可逆、密钥在自家 KMS；代价是要管好密钥与权限，并防止渲染层之外的旁路（导出、API 直查）。

① 入库

Presidio Anonymizer 以 encrypt 操作符加密敏感实体，trace 落库为密文 token；媒体原件走 S3 SSE-KMS。

② 展示

审计界面默认按掩码规则渲染，审计员无需接触密钥即可安全查阅对话记录。

③ 核验

合规主管经 KMS 授权解密单条记录还原原文，每次解密写入审计事件，全程留痕。

帮我联系下 张 *，电话 138****5678，身份证 110101********8515，邮箱 z*****i@example.com，卡号 6222 **** **** 0000。

审计界面默认渲染：掩码规则作用于渲染层，无密钥也能安全展示。

帮我联系下 张伟，电话 13812345678，身份证 110101199003078515，邮箱 zhangwei@example.com，卡号 6222 0202 0000 0000。

授权核验视图：仅合规主管经 KMS 授权可见，限单条、全程留痕。

帮我联系下 NAME_9f2c81e3，电话 PHONE_71b03ea7，身份证 IDCARD_3ad80712，邮箱 EMAIL_c4e12b90，卡号 CARD_8d51f004。

ClickHouse 实际存储的内容：AES-256-GCM 密文 token，同一实体每次加密结果不同，持 data key 才能解密。

演示为静态示意；真实密文由 Presidio Anonymizer 的 encrypt 操作符生成。掩码规则（张 *、138****5678 等）可按实体类型自定义。

角色默认看到能否还原原文典型用途
审计员掩码视图不可日常合规抽查、对话抽样审查
合规主管掩码视图，可申请还原可 · KMS 授权并留痕争议处理、安全调查核验
开发者掩码 + 技术元数据不可排障：token 用量、延迟、错误

防旁路要点：掩码只做在渲染层是不够的——API 与导出路径必须同样只返回密文 token 或掩码，原文只存在于解密服务之后；解密服务独立部署、单独审计。

中文识别要点：Presidio 需配中文 NLP 模型（如 zh_core_web_sm），身份证、手机号、银行卡用自定义 recognizer（正则 + 校验位，如 1[3-9]\d{9}、18 位身份证校验、Luhn）；中文人名召回一般，建议规则 + 模型混合，必要时用 OpenPipe pii-redact（LLM 检测）兜底。

08

多模态：图片与文件

请求里本来就是 URL

直接记录 URL 引用，不搬运文件。注意源可能失效，重要场景可异步镜像到自家 bucket。

base64 / 用户上传

先落对象存储（SSE-KMS 加密），再把消息里的 base64 替换成引用后才入 trace；否则单条 trace 轻松数 MB，拖垮存储与查询。

// 记录前：原始 message（数 MB）
{"type": "image_url", "image_url": {"url": "data:image/png;base64,iVBORw0…"}}

// 记录后：trace 里实际入库的内容
{"type": "image_url", "image_url": {"url": "s3://agent-media/2026/…/x.png"},
 "meta": {"sha256": "9f2c…", "bytes": 183421, "mime": "image/png"}}

存储选型注记：SeaweedFS 小文件性能与存储效率更好、许可宽松；MinIO 文档与生态最全。两者皆可，看运维熟悉度。

2埋点与标识符：SDK 装饰器（轻量编码）

# 骨架示意，API 以所用 SDK 版本文档为准
import hashlib
from langfuse import observe, langfuse_context

def pseudonymize(user_id: str) -> str:                # userId 假名化
    return "u_" + hashlib.sha256(user_id.encode()).hexdigest()[:12]

@observe()                                            # 根 span = 一次用户请求
def handle_request(req):
    langfuse_context.update_current_trace(
        session_id=req.conversation_id,               # conversation id
        user_id=pseudonymize(req.user_id),            # 假名后再上报
        tags=[f"agent:{req.agent_id}"],               # agent id 走 tag
    )
    return call_llm(req.messages)                     # 内部再包 @observe → generation span

自研框架提示：若不使用官方集成框架，手动埋三个关键点即可起步——请求入口、LLM 调用、工具调用；工具入参与返回摘要挂在 span 上。

3Presidio 中文脱敏管线（必须开发，数百行 + 调优）

# 骨架示意：模式 A 用 mask，模式 B 对敏感实体改用 encrypt
from presidio_analyzer import AnalyzerEngine, Pattern, PatternRecognizer
from presidio_anonymizer import AnonymizerEngine, OperatorConfig

PHONE = PatternRecognizer(supported_entity="CN_PHONE",
    patterns=[Pattern(name="cn-mobile", regex=r"1[3-9]\d{9}", score=0.95)])
# 同理注册：18 位身份证（校验位）、银行卡（Luhn）

analyzer = AnalyzerEngine(default_score_threshold=0.4, supported_languages="zh")
analyzer.registry.add_recognizer(PHONE)

def mask_pii(text: str, key: bytes) -> str:           # 挂到 Langfuse masking 回调
    r = AnonymizerEngine().anonymize(
        text=text,
        analyzer_results=analyzer.analyze(text=text, language="zh"),
        operators={
            "DEFAULT":  OperatorConfig("mask", {"masking_char": "*", "chars_to_mask": 4}),
            "CN_PHONE": OperatorConfig("encrypt", {"key": key}),  # 模式 B：可逆
        })
    return r.text

召回率调优是持续工作：中文人名 NER 一般，规则 + 模型混合，必要时用 OpenPipe pii-redact（LLM 检测）兜底。

4模式 B 审计展示层（最大自研部分，无现成开源整体方案）

audit-web · 审计前端

三级角色视图；默认掩码渲染；解密申请入口。可做得很薄：一个会话列表 + trace 详情页。

audit-api · 查询与渲染

查 Langfuse API 拉取 trace；渲染层统一掩码；API 与导出路径同样只返回密文或掩码——防旁路的关键在这里。

decrypt-svc · 解密服务

唯一持有 KMS data key 的组件；仅受理单条授权解密；每次调用写 append-only 留痕表，独立部署、单独审计。

减配路径：直接用 Langfuse UI 查看入库的密文 token，掩码 / 解密层全省，但审计员看到的是 NAME_9f2c81e3 这类内容，体验差；或在 LLM 网关层用 LiteLLM 的 Presidio guardrail（零代码，但只覆盖 LLM 调用入口）。

性能提示：Presidio 跑在 masking 路径有延迟开销（社区有实测反馈），上线前先压测；可只对命中敏感特征的请求启用，或异步补脱敏。

容量提示：多轮会话的 trace 体积膨胀快，ClickHouse 保留期建议先紧后松，S3 配生命周期归档，媒体桶与 trace 桶分开计费观察。
